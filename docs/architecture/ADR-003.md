# ADR-003: RulePack 规则抽象（可插拔规则包）

- **状态 (Status):** Accepted（含实现偏差）
- **日期 (Date):** 2026-08-13
- **决策者 (Deciders):** engineering-lead（基于代码事实反向梳理）
- **关联文档:** `ARCHITECTURE.md` §模块依赖关系、§运行时数据流；`ADR-001`（前端栈）、`ADR-002`（渲染/状态分离）

---

## 背景 (Context)

本项目是一个"成都麻将（血战到底）AI 教学平台"。麻将规则（牌型、阶段、碰杠胡、
定缺、换三张、结算）高度领域相关，且存在多地区变体。技术栈为 Vite + TypeScript，
运行时是单线程 `async` 游戏循环（`GameOrchestrator`）。需求是：在不改动
orchestration / agents / ui 的前提下，让规则成为可替换的"插件"，并为未来增加
其他麻将变体（如广东麻将、日本立直）留出扩展点。

**代码事实（证据）：**
- `src/core/rules/RulePack.ts:17-46` —— 定义了 `RulePack` 接口：
  `getTileSet / buildInitialState / getCurrentActor / getLegalActions /
  applyAction / collectReactions / resolveReactions / isRoundEnd /
  settleRound`，并带有可选 `getDiscardValidator()`；另定义了 `RoundResult`
  （`RulePack.ts:8-15`）。
- `src/core/rules/RuleRegistry.ts:3-21` —— `RuleRegistry` 类，内部 `Map<string,
  RulePack>`，`register / get（缺失即 throw）/ list`。
- `src/core/rules/packs/placeholder/index.ts` —— `placeholderRulePack`：仅实现
  `PLAYING` / `END` 两个阶段（`getLegalActions` 在 `phase !== 'PLAYING'` 时返回
  `[]`，见 `placeholder/index.ts:108`）；`collectReactions` 返回 `[]`、
  `settleRound` 返回 `{ placeholder: true }`（`:217-219`）。即"无碰杠胡/无定缺/
  无换三张"的简化骨架。
- `src/core/rules/packs/chengdu/index.ts:383` —— `chengduRulePack`：完整实现
  血战到底（含 `EXCHANGE` 换三张、`DING_QUE` 定缺、多玩家可胡、番数结算），是
  真正的生产规则实现。
- `src/orchestration/GameOrchestrator.ts:123-138` —— 构造函数签名为
  `rulePack: RulePack = placeholderRulePack`；内部 `new RuleRegistry()` 并
  `register(placeholderRulePack)`、`register(chengduRulePack)`。
- `src/orchestration/GameOrchestrator.ts:192-193` —— `init()` 中选择逻辑：
  `const selected = ruleId ?? this.ss.ruleId; this.rulePack =
  this.registry.get(selected);`（`this.ss` 即 `settingsStore`）。
- `src/store/settingsStore.ts:27,57` —— `ruleId` 默认值 `'chengdu'`，
  sanitize 时非 `'placeholder'` 一律归为 `'chengdu'`。

---

## 决策 (Decision)

采用 **RulePack 接口 + RuleRegistry 注册表** 的可插拔规则抽象：

1. 所有规则变体实现统一的 `RulePack` 接口；orchestration 仅依赖接口，不直接
   依赖任何具体规则实现。
2. 规则在启动时通过 `RuleRegistry` 注册；运行时由 `ruleId`（来自 `settingsStore`
   或 `startNewMatch(ruleId)` 入参）经 `registry.get()` 解析得到当前 `rulePack`。
3. 生产默认 `ruleId = 'chengdu'`（见 `settingsStore.ts:27`），因此部署版本实际
   运行的是完整的 `chengduRulePack`（血战到底），而非构造函数里的
   `placeholderRulePack` 默认值。

该设计满足"策略与引擎解耦"的目标：新增变体只需新增一个 `RulePack` 实现并
`registry.register()`，无需改动 `GameOrchestrator` 主循环或 `agents` 决策层。

## 后果 (Consequences)

**正面：**
- 清晰的领域边界：`core/rules` 是纯函数式规则引擎（`applyAction` 返回新
  `GameState`，无副作用），可被单测、`ai-eval` 与训练脚本直接复用（训练脚本
  `parallelTrainer.ts:193`、`gameWorker.ts:46`、`neuralTrainer.ts:133` 均直接
  `new GameOrchestrator(chengduRulePack)`）。
- 运行时切换成本低：`registry.get(ruleId)` 一次查表即得，且无运行时反射/动态
  加载开销。

**负面 / 偏离实现的事实（须在 REVIEW 中跟踪）：**
- **构造函数默认参数失效（死代码）：** `GameOrchestrator` 的
  `rulePack = placeholderRulePack` 默认参数在 `init()` 中总是被
  `registry.get(this.ss.ruleId)` 覆盖（`:193`），故该默认参数从未生效。
- **`selectRulePack()` 方法零调用：** 全仓 `grep selectRulePack` 结果为 0 处
  调用（`:193` 所在的选择逻辑内联于 `init()`），`selectRulePack` 是死方法。
- **分层违规（core → store）：** `core/rules/packs/chengdu/index.ts:14`
  `import { settingsStore } from '../../../../store/settingsStore'` 并在
  `:255 / :470 / :472 / :510` 直接读取 `settingsStore.p0IsAI`。这使
  `core`（应为基础纯层）反向依赖了 `store`（UI/配置层），破坏单向依赖纪律
  （详见 `ARCHITECTURE.md` 违反表）。
- **`placeholder` 与 `chengdu` 能力不对等：** `placeholder` 仅 `PLAYING/END`，
  而 `chengdu` 含 `EXCHANGE/DING_QUE` 等多阶段；二者并非"同一接口的不同等价
  实现"，更像"测试骨架 vs 生产实现"。这会让"切换规则包"在 UX 上行为差异巨大，
  需在 UI（`settings.ts:342` 的 `ruleId: 'chengdu'` 选项）中明确约束可用集合。

## 备选方案 (Alternatives Considered)

| 方案 | 描述 | 未采纳原因 |
| --- | --- | --- |
| A. 单一硬编码规则 | 直接在 `GameOrchestrator` 内写死成都规则 | 无法复用/测试/扩展，违反本项目"可插拔"目标 |
| B. 策略模式 + 注册表（已采纳） | `RulePack` 接口 + `RuleRegistry` 查表 | —— |
| C. 动态 import / 远程规则包 | 运行时从 CDN 加载规则包 | 增加供应链与类型安全风险；当前变体少，过度设计 |
| D. 配置驱动（data-only 规则） | 用 JSON 描述规则参数 | 麻将阶段机与结算逻辑复杂，纯数据难以表达，最终仍需代码 |
