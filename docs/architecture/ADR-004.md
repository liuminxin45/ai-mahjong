# ADR-004: LLM 表达层与决策层分离

- **状态 (Status):** Accepted
- **日期 (Date):** 2026-08-13
- **决策者 (Deciders):** engineering-lead（基于代码事实反向梳理）
- **关联文档:** `ARCHITECTURE.md` §模块依赖关系（llm / analysis / agents 分层）；
  `ADR-003`（规则可插拔）

---

## 背景 (Context)

本平台既是"可运行的对局引擎"，也是"AI 教学平台"。其中一个核心诉求是用 LLM
（如 Kimi / OpenAI 兼容接口）为玩家提供**自然语言讲解、出牌建议、复盘、问答**。
但 LLM 具有非确定性、时延高、可能返回非法内容等特征，绝不应参与**决定棋盘上
实际走哪一步**的闭环——否则会出现"模型幻觉导致非法落子""网络超时卡死整局"
"不可复现的对局"等问题。

**代码事实（证据）：**
- **决策层（确定性、纯函数）：**
  - `src/agents/algo/policy_high.ts` —— `decideHigh(...)` 基于 EV（期望收益）
    做决策，并含 `fastDiscardDecision`（训练模式快速出牌）。
  - `src/agents/algo/difficulty.ts` —— `policyForDifficulty()` 当前仅返回
    `decideHigh`（唯一难度档 `'high'`，见 `settingsStore.ts:1`）。
  - 支撑模块：`bloodBattleEV.ts`、`expectedValue.ts`、`aiParams.ts`（可在线
    学习调整的参数）。
  - 调用点：`GameOrchestrator.ts:144-146` 为 P1/P2/P3 装配
    `pickAlgoAction(s, pid, legal, this.ss.difficulty, ctx)`，决策走确定性 EV。
- **表达层（非确定性、面向人）：**
  - `src/llm/LLMService.ts` —— `getCoachingAdvice()`（`:189-198`）调用
    `PromptBuilder.buildCoachingPrompt(...)` 并向 LLM 提问，解析为
    `CoachingAdvice`。注意 `:196` 使用 `useCache:false`（每次都打网络）。
  - `src/llm/PromptBuilder.ts` —— 纯函数构造各类提示词（出牌建议、换三张、
    定缺、复盘、用户画像、问答、解说、对手预测），**不调用任何规则/决策 API**。
  - `src/analysis/LLMAnalyzer.ts` —— `LLMAnalyzer` 接口与
    `OpenAICompatibleLLMAnalyzer` 实现（`explainDecision / chat / summarizeMatch
    / explainForHuman / summarizePopulationInsights` 等），全部是**文本生成**。
  - `src/analysis/HeuristicAnalyzer.ts` —— `recommendDiscards / analyzeHand`
    提供确定性弃牌建议（UI 侧展示用）。
- **关键边界证据：** `grep` 全仓 `buildCoachingPrompt|recommendedAction`，命中
  仅 `PromptBuilder.ts`（构造）、`LLMService.ts:195,489`（产出）、
  `types.ts:60`（类型）、`LLMChatAssistant.ts:774`（`formatRecommendedAction`
  **仅用于 UI 展示**）。**没有任何代码将 LLM 的 `recommendedAction` 喂回
  `applyAction` / `getLegalActions` / 游戏主循环。**
- **降级证据：** `LLMService.ts:486-500` `getDefaultCoachingAdvice()` 在 LLM
  缺失/失败时回退到"基于基本策略的建议"（取第一个 DISCARD）。UI 在
  `llmEnabled=false` 时不调用 LLM（`settingsStore.ts:11,29`）。

---

## 决策 (Decision)

明确将系统划分为两条互不耦合的链路：

1. **决策层（Game Loop / Decision Plane）**：由 `GameOrchestrator` 驱动，
   通过 `agents/algo/*` 的确定性 EV 策略产生每一步合法动作。该链路**不依赖
   任何 LLM**，结果可复现、可单测、可在无网络环境下完整运行。

2. **表达层（Expression / Coaching Plane）**：由 `llm/*` 与 `analysis/*`
   组成，消费**当前已发生的局面快照**，生成面向人的文本（建议理由、复盘、
   问答、解说）。其输出（含 `CoachingAdvice.recommendedAction`）**仅供 UI 展示
   与教学**，不回灌决策闭环。

3. 两条链路仅通过"只读的游戏状态快照"与"已落子的历史"通信；表达层不持有
   游戏推进权。LLM 失败时整体降级为启发式建议或关闭，不影响对局可玩性。

## 后果 (Consequences)

**正面：**
- **健壮性：** LLM 超时/限流/返回非法 JSON（`parseJSONStrict` 抛错）只影响
  "教学文案"，绝不会让棋盘进入非法状态或卡死主循环。
- **可复现 & 可测：** 对局逻辑与 AI 强度评估（`testing/ai-eval/*`）完全脱离
  LLM，174 项单测与 AI 评测可在离线环境稳定通过。
- **安全：** 敏感 Key 经 Vercel 函数代理隔离（见 `ADR-001` / `REVIEW.md`
  Security checkpoint），前端只持有一个可配置 endpoint，不直接暴露密钥。

**负面 / 须关注：**
- **两套"建议"源可能不一致：** UI 既可能展示
  `HeuristicAnalyzer.recommendDiscards`（确定性），也可能展示
  `LLMService` 的 `CoachingAdvice`（非确定性）。二者口径不同时会让教学信息
  自相矛盾，需明确"以哪一套为权威建议、另一套作补充"。
- **LLM 建议的教学价值有限：** `CoachingAdvice.recommendedAction` 的默认值是
  "玩家自己已打出的那张牌"（`LLMService.ts:489`），即更多是"复盘式回声"而非
  "独立裁判"。若目标是"指出更优解"，应让表达层直接消费
  `HeuristicAnalyzer` 的 EV 排序结果，而非让 LLM 重新拍板。
- **缓存缺失导致成本/时延：** `getCoachingAdvice` 固定 `useCache:false`
  （`:196`），相同局面每次都打 LLM，既有费用也有交互时延风险，建议对局面
  哈希做客户端缓存。

## 备选方案 (Alternatives Considered)

| 方案 | 描述 | 未采纳原因 |
| --- | --- | --- |
| A. LLM 直接决策 | 让 LLM 解析局面并落子 | 非确定性、易出非法动作、超时卡死、不可复现、无法离线 |
| B. 决策/表达分离（已采纳） | 确定性 EV 决策 + LLM 仅做表达 | —— |
| C. LLM 投票/集成决策 | 多模型投票决定落子 | 复杂度与成本激增，且未解决可复现问题；教学平台无需 |
| D. 纯规则教学（无 LLM） | 只用 `HeuristicAnalyzer` 文本化 | 失去自然语言交互与开放问答的教学体验，违背产品定位 |
